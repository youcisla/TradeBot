# TradeBot — Audit Findings, 2026-09-13

Account audited against: PU Prime **DEMO** 700174321 (EUR, balance €1,000), server `PUPrime-Demo`.
Scope: full codebase (48,026 lines Python, 159 TS/TSX files, 413 tracked files), verified by
running the code, not by reading it alone.

**Relationship to existing plans.** `.claude/plans/implementation_plan.md` (v2.0, 2026-04-30) is a
forward-looking rebuild plan. This document is an audit of the tree as it exists today. It does not
replace that plan and does not restate its targets. Notably, that plan already sets 1% risk per
trade as a hard cap and a <10% maximum drawdown — the position in §5 below is consistent with it,
not in conflict.

---

## 1. Executive summary

The single most important finding: **the bot has never been able to connect to a real broker.**

`adapters/mt5/connector.py` declared `class MT5Connector(BrokerConnector)` but implemented only
the connection lifecycle. `BrokerConnector` is an ABC requiring 13 methods; the order methods
live as module-level functions in `order_executor.py`. The inheritance therefore made the class
abstract and **impossible to instantiate**, so `broker/mt5_connector.py` raised `TypeError` during
construction. Every live MT5 code path was dead — including the backtest CLI's own data fetch.

The 320-test suite passed throughout, because every test uses `MockConnector`. No test constructed
the real broker.

This is now fixed and verified: the connector constructs, connects, reads balance (€1,000) and
returns candles.

Two further conclusions:

- **The backtest cannot establish whether the strategy has an edge.** It contains a hard look-ahead
  in higher-timeframe data and models zero transaction costs.
- **The money-critical path has multiple confirmed defects.** Most severe: every "partial" close
  closes the entire position, so the TP1/TP2/TP3 scale-out design does not function at all.

## 3. Backtest validity audit

**Verdict: the current backtest cannot establish a genuine edge.**
The two artifacts that look rigorous (`backtesting/walk_forward.py`,
`baseline_benchmarks.py`) never touch the ICT strategy — they only score toy baselines.

Ranked defects:

1. **HTF look-ahead (severe).** `scripts/backtest.py:244-258` builds H4 by grouping the *entire*
   H1 array and returning the tail. At bar *t* the HTF bias, dealing range, FVG and OB are
   computed from H4 bars containing H1 candles *after t*. Every HTF-gated setup is partly decided
   by the future. This alone invalidates the results.
2. **Zero transaction costs.** `scripts/backtest.py:189-192` sets `spread=0.0`; no commission,
   swap or slippage. Live EURUSD spread is 15 points (1.5 pips) — a large fraction of a 1×ATR
   target.
3. **No out-of-sample / walk-forward for the strategy.** One in-sample pass with fixed parameters.
   The CLI *is* the tuning loop, so every number is in-sample. No holdout exists.
4. **Phantom limit fills and full-position credit.** `_simulate_trade` never checks that the limit
   level was actually touched, yet counts the entry as filled. A TP3 win is credited the full
   `(tp3-entry)/r_dist` even though live management banks 40/30/30 at TP1/2/3. Wins are overstated
   materially.
5. **Metric errors.** `backtesting/report.py:25` treats `pnl >= 0` as a win, so breakeven legs count
   as wins. Each TP leg is counted as a separate trade, tripling *n* with correlated observations.
   Sharpe is trade-basis, not annualized. The equity curve is additive.
6. **Hindsight fed into live confidence.** `scripts/backtest.py:734-745` seeds each strategy's live
   confidence from its *best symbol's* score.

Clean: swing detection uses left/right confirmation without future bars; SL is checked before TP
within a bar; the max-drawdown high-water calculation is correct; the purged walk-forward generator
is sound — it is simply never used.

## 4. Money-critical path audit

All items CONFIRMED by tracing the code path unless marked SUSPECTED.

1. **`close_partial` closes the ENTIRE position.** `adapters/mt5/order_executor.py:194,207-210`
   computes `requested_volume` then never uses it, sending the full live volume instead. Every TP1
   partial close exits 100% of the position — the scale-out design is dead. The subsequent
   `_reconcile_partial_close` then sees no position and reports a clean close, so the error is
   invisible in logs.
2. **Lot size booked differs from lot size traded.** `agents/execution_agent.py:142,150-154` builds
   `Trade.lot_size` and the TP splits from the requested size, but `normalize_volume` rewrites the
   wire volume (to `FIXED_LOT_SIZE`). `result.filled_lots` is set and never read anywhere. All local
   bookkeeping — remaining lots, TP splits, expected P&L, commission — is wrong relative to the
   broker. At 0.01 lots, `tp1_lots = round(0.01 * 0.40, 2) = 0.00`, so the split machinery
   degenerates entirely.
3. **Order retcodes drop live positions.** `order_executor.py:130-146` treats only
   `TRADE_RETCODE_DONE` as success. An IPC timeout (`None`) or `TRADE_RETCODE_DONE_PARTIAL`
   (10010) is reported as failure, and the caller returns `None` without a position lookup or the
   `_confirm_position_open` watchdog. Result: a real position at the broker with no DB row and no
   manager — an unmanaged orphan.
4. **GuardPipeline fails OPEN.** `agents/guards.py:500-516` logs and skips any guard that raises. A
   crashed drawdown, whitelist or market-hours guard silently disappears. Safety gates must fail
   closed.
5. **DailyDrawdownGuard cancels realised losses.** `guards.py:230-238` computes
   `starting_balance + realised_pnl - equity`, but equity already reflects realised P&L, so the
   term cancels — a day of closed losses reports ~0 drawdown. The threshold is also hardcoded
   `0.05` at `:472`, ignoring `MAX_DAILY_LOSS`.
6. **SL divergence.** `agents/trade_manager.py:347-348` (breakeven) and `:683-691` (trailing) set
   `trade.stop_loss` regardless of whether the broker's `modify_order` succeeded. Local state can
   show a tightened stop that the broker never applied.
7. **TP reconciliation is dead code.** `trade_manager.py:100` only processes positions whose comment
   contains `_TP1/_TP2/_TP3`, but `order_executor.py:122` sets the comment to the strategy name.
   The repair path never runs. `state/persistence.py:91-98` uses the same probe, so adopted orphans
   get `TP=0` and can never take profit.
8. **Whitelist suffix stripping breaks on PU Prime symbols.** `guards.py:104` uses
   `sym.rstrip("m.r_")`, which cannot strip the `.s` suffix used by `config.symbols.PRIORITY_SYMBOLS`
   (`EURUSD.s`). SUSPECTED in impact — depends on the runtime symbol strings — but the mechanism is
   confirmed.
9. **Daily-loss cap is pre-trade only.** Post-breach, an open position can continue to run, and a
   60-second cache permits up to 60s of new entries after a breach is realised.

Well-handled: `close_order` is idempotent; `close_partial` re-checks position existence before
retry; startup reconciliation adopts orphans and closes DB-only trades; `_confirm_position_open`
watchdog; slippage guard with emergency close; broker-authoritative contract/tick size lookups;
signal geometry validation.

## 5. On the goal "2X the balance each time"

This target should be replaced, for two reasons.

**It is a sizing instruction, not a strategy.** Doubling per cycle is exponential. Reaching it
quickly requires risking a large fraction of equity per trade, and over-betting past the
growth-optimal (Kelly) fraction *reduces* expected growth and *raises* ruin probability. With a
genuinely good edge — 55% win rate, 1.5:1 payoff — Kelly is roughly 25% of equity per trade,
already reckless for a real system. At twice Kelly, expected growth is exactly zero. At a sane 1%
risk per trade, that same edge compounds about 0.37% per trade, so doubling takes roughly 189
trades.

**The edge is unproven.** Nothing in this repository demonstrates positive expectancy out-of-sample,
and per §3 the existing backtest is not capable of demonstrating it.

Revised success criteria, in order:

1. A measurement pipeline that is trustworthy — no look-ahead, real costs, purged walk-forward, and
   a frozen holdout nobody tunes against.
2. A demonstrated positive expectancy on unseen data.
3. A drawdown the account can survive, with risk limits enforced in code.
4. Compounding as an outcome, not as a per-cycle target.

## 6. Master plan

### Phase 0 — Measurement (do first; it can change everything downstream)
- Rebuild the backtest data path with **as-of slicing** on every timeframe. HTF series must be built
  only from bars at or before the decision timestamp.
- Add a **cost model** to every fill: buy at ask / sell at bid from real spreads, plus commission and
  swap. Require limit entries to be genuinely touched.
- Wire the existing purged/embargoed **walk-forward** and freeze a final holdout.
- Report per-**position** statistics (not per-leg), annualized Sharpe, max drawdown and an equity
  curve, alongside a buy-and-hold baseline.
- Deliverable: one report with win rate, expectancy, max drawdown, Sharpe and the equity curve — or
  an honest statement that there is no edge.

### Phase 1 — Correctness and safety (before any live capital)
- Fix defects 1–7 in §4. Priority: `close_partial` (1), lot-size divergence (2), orphan positions
  on retcode (3).
- Make GuardPipeline **fail closed**.
- Reconcile broker state on startup and after every reconnect; treat the broker as the source of
  truth for position size and stops.
- Add an immutable outer risk envelope: max lot, max concurrent positions, max daily loss, max
  drawdown — constants the adaptive layer cannot modify.
- Add a kill switch with a single command path (Telegram and file flag).

### Phase 2 — Observability
- Dashboard reports *measured* state, not intended state.
- Telegram alert on every fill, block, rejection, guard trip and drawdown breach.
- Health endpoint: connection state, last iteration time, open positions versus broker.

### Phase 3 — Always-on operation
- Process supervisor with restart-on-crash and backoff.
- Heartbeat file plus external watchdog.
- Session scheduling, with the `MarketHoursGuard` weekend inconsistency fixed.
- Position reconciliation loop independent of the trading loop.

### Phase 4 — Bounded self-evolution (only after Phases 0–3)
- The adaptive layer may tune strategy parameters and confidence **within** the Phase 1 envelope.
  It must not be able to edit that envelope.
- Every automated change is logged with its justification and is reversible.
- Promotion of a parameter change requires out-of-sample improvement, not in-sample fit.
- Never wire backtest output directly into live confidence (§3 defect 6).
